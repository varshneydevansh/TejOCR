# TejOCR 0.2.1

`0.2.1` is the current release. It should be read as a focused follow-up to `0.2.0`, not a new architectural reset.

In short:

- `0.2.0` made the extension much more polished and structured.
- `0.2.1` makes that polished surface more reliable in real-world setup, clipboard, and PDF/runtime edge cases.

## Delta From 0.2.0

### 1. Setup & Diagnostics became a stronger install surface

Compared with `0.2.0`, `0.2.1` puts much more weight on the setup experience:

- LibreOffice Python is now surfaced more explicitly.
- The dialog distinguishes:
  - core OCR readiness,
  - PDF readiness,
  - optional Python extras.
- Users can now:
  - copy a support snapshot,
  - save setup commands as a script,
  - open the install guide directly from the dialog.
- A Windows-first helper script now exists at:
  - [scripts/tejocr_windows_bootstrap.ps1](../../scripts/tejocr_windows_bootstrap.ps1)

This release is much more install/support friendly than `0.2.0`, especially for users who are new to LibreOffice Python.

### 2. Setup/readiness status is more truthful

`0.2.0` still had some tension between the main Settings summary and the deeper diagnostics view.

`0.2.1` improves that by separating readiness signals for:

- `Tesseract`
- `PDF`
- `Extras (optional)`

That means the extension can now show a clearer distinction between:

- core OCR ready,
- PDF OCR ready,
- optional extras not installed.

### 3. Clipboard copy flows are more robust

`0.2.1` strengthens clipboard behavior in both setup/support copy flows and shared OCR text transfer logic:

- the UNO clipboard transferable now advertises multiple plain-text flavors,
- macOS copy fallback now tries `pbcopy` and then `osascript`,
- support-copy actions are less likely to fall back immediately to manual selection.

This is a reliability improvement over `0.2.0`, not a surface redesign.

### 4. PDF/runtime subprocess decoding is safer

`0.2.1` also fixes a real PDF/runtime failure class:

- OCR/PDF subprocess output is now decoded using UTF-8 with replacement,
- non-ASCII stderr/stdout no longer causes ASCII codec crashes during OCR/PDF processing.

This matters most for users who were seeing OCR fail with decode errors even though the PDF renderer and Tesseract were installed correctly.

### 5. Docs and install guidance are tighter

The documentation and setup guidance now better reflect the actual runtime model:

- LibreOffice Python is called out more clearly,
- Windows install steps are more explicit,
- troubleshooting/install docs are cleaner and better formatted,
- package/license metadata guidance is easier to follow.

## What Stayed The Same From 0.2.0

The visible UI work from `0.2.0` remains the foundation:

- structured `OCR Complete`,
- refined Settings / Help / Setup surfaces,
- `A Message` dialog,
- `6 pt` Writer OCR output default,
- cleaner dialog-family styling.

`0.2.1` does not replace that work. It stabilizes and supports it better.

## Practical Release Framing

If someone asks what changed between `0.2.0` and `0.2.1`, the shortest accurate answer is:

> `0.2.0` polished the TejOCR interface. `0.2.1` made setup, clipboard handling, and PDF/runtime behavior more reliable in real use.
