# TejOCR 0.2.0

`0.2.0` is the UI-consolidation release that sat on top of the OCR/runtime hardening from `0.1.9`. It has since been followed by `0.2.2`.

In short:

- `0.1.9` made the OCR pipeline more truthful, bounded, and measurable.
- `0.2.0` makes that hardened pipeline easier to use, easier to install, and easier to understand inside LibreOffice.

## Delta From 0.1.9

### 1. Result UX moved from log dump to structured dialog

Compared with `0.1.9`, `0.2.0` now presents successful OCR completion in a dedicated `OCR Complete` dialog instead of relying on dense message-box style output.

That dialog now includes:

- a grouped `Result Summary`,
- a dedicated `Source Breakdown`,
- a cleaner `OCR Profile`,
- a separate `Runtime Diagnostics` block,
- requested-vs-effective details that no longer collapse into a single unreadable line,
- and a scrollable source list for larger mixed image/PDF batches.

This is the most visible user-facing difference between `0.1.9` and `0.2.0`.

### 2. Settings surface is more product-like

`0.2.0` also adds the `A Message` action in the main Settings dialog.

That new dialog exists to explain:

- why TejOCR exists today,
- why it is still a workaround,
- what native LibreOffice support could unlock,
- and how users can ask for stronger upstream OCR/document intelligence support.

The dialog also exposes the aKriti direction and includes a direct open action rather than leaving that information buried in plain text.

### 3. Writer output defaults changed

`0.2.0` changes the inserted OCR text presentation in Writer:

- inserted OCR text now defaults to `6 pt`,
- this applies to:
  - insert at cursor,
  - create text box,
  - replace image,
- clipboard output remains plain copied text and is not styled.

This is a deliberate Writer-output change relative to `0.1.9`.

### 4. Settings and parameter persistence regressions were fixed

During the UI iteration after `0.1.9`, several save/persistence regressions surfaced. `0.2.0` fixes those, including:

- `preview_control` save failures,
- incomplete persistence for preset/grayscale/binarize values,
- and cleanup around advanced PSM/OEM value handling.

So `0.2.0` is not only more polished visually, it is also more reliable when the newer settings UI is used.

### 5. Packaging/install metadata is stricter and safer

`0.1.9` improved release/build documentation. `0.2.0` carries that through into a concrete installer fix:

- `description.xml` no longer uses invalid `simple-license` metadata that could break installation on stricter LibreOffice environments,
- Windows install failures of the form:
  - `Could not obtain path to license. Possible error in description.xml`
  were traced and fixed,
- metadata validation tests now guard that packaging path.

This means `0.2.0` is a stronger packaging release than `0.1.9`, especially for Windows users.

## What Stayed The Same From 0.1.9

The core OCR/runtime model introduced in `0.1.9` remains the foundation:

- bounded OCR preset behavior,
- requested-vs-effective runtime diagnostics,
- page-streamed PDF OCR,
- adaptive PDF DPI policy,
- safer LibreOffice Python helper detection,
- benchmark/test coverage around the hardened runtime.

`0.2.0` does not replace that work. It productizes it.

## Practical Release Framing

If someone asks what changed between `0.1.9` and `0.2.0`, the shortest accurate answer is:

> `0.1.9` hardened the OCR engine and runtime semantics. `0.2.0` turned that into a cleaner LibreOffice experience with better dialogs, better packaging/install behavior, and better Writer output defaults.
